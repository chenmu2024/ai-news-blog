# 别再让AI只写代码：把GitHub Issue变成自动交付线

**作者：陈慕**

哈喽，大家好，我是陈慕。

如果你是一人公司，最近大概率已经体验过一种很奇怪的效率提升：以前一个页面要写半天，现在把需求交给 Codex、Claude Code 之类的编码 Agent，几十分钟就能看到结果。

但用久以后，真正拖慢你的往往已经不是“代码写得够不够快”。

而是另一堆事情：需求有没有拆清楚？Agent 改错了怎么办？测试谁跑？改完谁检查？多个任务能不能并行？今天关掉电脑，明天还能不能知道任务走到哪一步？

这也是我最近更关注的一类开源项目：**不是再造一个更会写代码的 Agent，而是给多个编码 Agent 加一条生产线。**

我看到一个很典型的项目叫 chipping-orchestrator。它的思路非常直接：把 GitHub Issue 变成任务入口，然后让 Claude Code、Codex CLI 等编码 Agent 分工完成规划、实现、验证和审查，最后生成 Pull Request，真正的合并仍然交给人。

这个方向对一人公司很重要，因为我们下一阶段缺的可能不是“更强的 AI 程序员”，而是**一个不用你一直盯着 AI 程序员的项目经理。**

## 现在最大的浪费，是你自己在给Agent当调度员

很多人的 AI 编程流程其实还是手工作坊。

想到一个需求，打开聊天窗口；让 AI 改代码；跑一下；报错了，把错误复制回去；修好以后再让另一个模型看看；最后自己提交 Git。

AI 确实写了大量代码，但人一直坐在中间搬运上下文。

如果一天只有一个任务，这没什么问题。

可当你同时维护几个网站、SaaS、自动化脚本时，情况马上变了。

首页要改一个模块，SEO 页面有一个 bug，支付回调需要补测试，另一个项目又要增加新功能。真正占注意力的不是某个任务本身，而是不断切换：这个做到哪了？那个测试了吗？哪一个需要我决定？

chipping-orchestrator 给我的启发就在这里。

它没有把所有工作塞给一个“万能 Agent”，而是把开发过程变成状态机。一条 Issue 会经历拆解、准备、实现、验证、文档、审查等状态。大的需求还能被拆成子 Issue；实现 Agent 在独立的 git worktree 中工作；审查 Agent 可以要求继续修改；最终 Pull Request 停在人类审核这一关，不自动合并。

这套设计看起来比“帮我写一个功能”复杂，但它解决的是一人公司真正会遇到的第二阶段问题：**当 AI 的执行速度超过人的管理速度以后，怎么管理 AI。**

## 我更看重的，不是多Agent，而是“状态不会丢”

很多 Agent Demo 都很惊艳，但关掉会话以后就很尴尬。

昨天做到哪里、为什么这么改、还有什么没完成，往往依赖聊天记录。

而这个项目把工作流状态直接放在 GitHub Issue 上。

这意味着任务不是“存在某一次聊天里”，而是存在项目本身。进程重启以后，状态仍然可以继续；人打开 GitHub，也能看到任务目前处于 decomposing、implementing、validating 还是 in review。

我觉得这是一个很值得独立开发者借鉴的产品原则：

**不要把 Agent 的记忆当成业务状态。**

真正重要的状态应该落到数据库、Issue、工单、CRM、订单或者其他可审计的系统里。模型可以换，会话可以断，任务状态不能跟着消失。

这个原则不仅适用于写代码。

你完全可以把它迁移到内容生产：选题 → 调研 → 初稿 → 核验 → 排版 → 待发布。

也可以迁移到 SEO：关键词发现 → 数据验证 → SERP 分析 → 页面生成 → QA → 上线 → 收录检查。

甚至可以迁移到销售：线索发现 → 资格判断 → 个性化触达 → 回复分类 → 人工确认 → 跟进。

真正可复用的东西，不是“多 Agent”三个字，而是**让每一个任务都有状态、有责任人、有退出条件、有人工闸门。**

## 如果是我，我不会一上来就做全自动开发公司

看到这种项目，很容易产生一个冲动：把整个开发流程全部自动化，然后晚上睡觉，Agent 自己写十个功能。

我不会这么做。

第一版我只会挑一种任务：**低风险、验收标准明确、失败可以回滚。**

例如给现有网站修一个明确的 UI 问题、补一个测试、修复一个已经复现的 bug、修改结构化数据、补内部工具的小功能。

Issue 里必须写清楚四件事：现在是什么问题、希望变成什么样、哪些文件或功能不能碰、怎样才算完成。

然后让规划 Agent 先拆任务，实现 Agent 写代码，验证阶段跑测试，再让一个不同的 Agent 做审查。

最后仍然由我决定是否合并。

这样做的价值不是“完全无人化”，而是把我从执行链路里拿出来，只留在两个地方：**定义结果，以及批准高风险动作。**

这其实和管理真人团队很像。

老板不应该每天坐在程序员旁边告诉他下一行代码怎么写。老板应该把需求和边界说清楚，在关键节点验收。

Agent 时代也是一样。

## 这里面真正值得做的生意，可能不是再做一个编程Agent

如果把视角从“我自己怎么用”切换到“什么可以卖”，我觉得机会反而更清楚。

基础模型公司会继续把编码能力往上推，通用编程 Agent 也会越来越强。一个独立开发者再做“比 Codex 更会写代码”的产品，难度很高。

但围绕 Agent 的**调度、验证、治理和行业工作流**，仍然有很多细分空间。

例如给 WordPress Agency 做一个维护 Agent：客户提交 Issue 后自动复现、修改测试站、跑视觉检查，生成变更说明，最后等人工批准上线。

给 SEO 团队做一个技术修复 Agent：从爬虫报告里接收问题，自动定位模板、生成修改、检查 canonical、schema、内链和页面渲染，最后生成 PR。

给小型 SaaS 团队做一个 bug triage Agent：读取用户反馈，合并重复问题，复现、分级，再把确定的问题送进编码队列。

这些产品卖的都不是“AI 会写代码”。

卖的是：**一个原本需要人反复协调的流程，现在可以稳定地从入口走到待批准结果。**

这类产品还有一个好处：价值比较容易计算。

如果一个 Agency 每周有几十个小修改，以前负责人要不停分配、追踪、检查；现在系统能自动完成前面 80% 的流程，负责人只处理异常和最终审批，那么节省的不是几次模型调用，而是项目管理时间。

这才有机会形成持续付费。

## 但这里有一个不能忽略的风险：权限

越是能自主工作的 Agent，权限问题越重要。

chipping-orchestrator 的文档自己就明确提醒：Agent 运行时可以关闭自身的审批和沙箱检查，因此运行它的主机账户本身就是安全边界；项目也要求使用具有限定权限的 GitHub Token，并建议公开仓库限制允许触发任务的 Issue 作者。

这个细节非常重要。

如果你未来做任何“常驻 Agent”，都不要只问它能不能完成任务，还要问：它拿到了什么权限？谁能给它下指令？它能不能删除数据？能不能直接发布？能不能付款？失败以后有没有审计记录？

我的原则会很简单：

**AI 可以自动做可逆动作，高风险动作必须留一个人工闸门。**

代码可以自动生成 PR，但不要默认自动合并生产环境；文章可以自动生成草稿，但不要默认群发；广告可以自动提出调整方案，但大幅改预算要确认。

自动化越强，这个边界越值钱。

## 今天就能做的，不是安装项目，而是先改你的工作方式

你甚至不用马上部署任何多 Agent 框架。

先打开自己的 GitHub，把最近经常交给 AI 的任务看一遍。

挑一个重复最多的流程，然后把它写成一条固定链路。

比如：

需求进入 Issue → AI 判断是否信息完整 → 不完整就停下 → 完整则生成计划 → 编码 → 自动测试 → 第二个 Agent 审查 → 生成 PR → 人工合并。

跑十次以后再看，哪一步最经常失败，哪一步最浪费你的时间，哪一步其实根本不需要人。

这时候你才知道自己真正需要自动化什么。

我越来越觉得，一人公司使用 AI 的分水岭，不是用了多少模型，而是有没有从“我不断给 AI 发指令”走到“我设计一个系统，让 AI 在系统里工作”。

前一种方式让一个人干得更快。

后一种方式，才开始让一个人拥有团队的杠杆。

而这也是我现在看 AI 项目时最想找的机会：**不是再造一个聪明的聊天框，而是把一份真实工作，变成一条能自己往前走、只在关键节点找人的生产线。**
